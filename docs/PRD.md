# 产品需求文档（PRD）· A股板块新闻监控系统

> 产品名称：A股板块新闻监控系统（stock_news）  
> 文档版本：V1.4  
> 产品状态：已上线（Streamlit Cloud），持续迭代  
> 更新日期：2026-07-17  
> 作者：Wang Yijie

## 1. 背景与问题

A 股个人投资者往往按「板块 / 行业」组织自己的投资逻辑，例如半导体、创新药、低空经济，但主流资讯产品通常按「个股」或「时间流」组织信息。用户真正想快速回答的是：

> 我关注的板块今天发生了什么？是利好还是利空？

核心痛点：

- **信息分散**：同一事件在多个媒体重复出现，标题各异，需要用户自行去重与辨别。
- **缺少方向判断**：新闻本身不直接说明对板块是利好还是利空，判断门槛高、耗时长。
- **宏观事件传导不透明**：美联储议息、出口管制等外部事件会传导到具体板块，但资讯产品通常不呈现这条链路。
- **被动获取困难**：政策、制裁等盘中高影响消息需要主动刷新闻，容易错过。

### 1.1 现有方案与差距

| 现有方案 | 优势 | 主要差距 |
|---|---|---|
| 东方财富 / 同花顺资讯流 | 信息全、更新快 | 时间流组织、噪声大；缺少板块维度方向判断 |
| 财联社电报 | 快讯速度快、简洁 | 不按板块聚合，不做利好/利空标注 |
| 雪球等社区 | 有观点与讨论 | 噪声大、质量参差、时效性不稳定 |
| 人工浏览 + 自建表格 | 符合个人逻辑 | 每日耗时高，无法覆盖盘中 |

## 2. 产品定位与目标

### 2.1 产品定位

面向 A 股个人投资者的**板块级新闻监控与解读工具**：以板块为一级组织单位，自动完成：

**采集 → 分类 → 方向判断 → 推送**

产品定位是投资决策前的**信息预处理层**，不提供投资建议。

### 2.2 产品原则

1. **板块优先**：个股与宏观事件最终都映射回板块。
2. **判断透明**：每个利好/利空标签附带命中理由与置信度，可解释、可追溯。
3. **宁缺毋滥**：推送只发送政策类或高影响新闻，并限制数量。
4. **零成本运行**：优先使用免费基础设施；LLM 仅按需触发并缓存。

### 2.3 北极星指标

用户每天用 **≤ 3 分钟**（一次页面浏览或一条推送）即可掌握关注板块的当日关键动态。

## 3. 用户画像与核心场景

### 3.1 目标用户

有 1–3 年经验的 A 股个人投资者：按行业板块构建持仓与自选逻辑，每天愿意花在信息收集上的时间有限（10 分钟以内），有基本的信息辨别能力，但没有专业终端（Wind、Choice）的预算。

### 3.2 核心场景

**场景 A · 早间速览**  
7:30 通勤路上，用户收到每日早报：关注板块的隔夜与早间新闻已按重要性排序并标注利好/利空，2 分钟内完成浏览。

**场景 B · 盘中异动提醒**  
交易时段出现高影响新闻后，系统在目标时效内抓取并识别为政策类 / 高影响，推送到微信或 Telegram，用户可点击原文核实。

**场景 C · 晚间个股复盘**  
用户搜索某只股票后，一页查看个股行情与基本面摘要、关联板块、直接相关新闻及关联板块新闻。

## 4. 整体方案与信息架构

### 4.1 系统链路

```text
定时任务（交易时段每 30 分钟）
        ↓
采集：多关键词并发抓取（AKShare / 东方财富搜索）
        ↓
分类：规则引擎初筛 ── 低置信度 ──→ LLM 复核（结果缓存）
        ↓
存储：Supabase Postgres（本地 CSV 自动兜底）
        ├─→ 推送：政策类 / 高影响新闻 → 微信 / Telegram
        ↓
展示：Web 面板 → 板块新闻 / 热点 / 摘要 / 个股搜索
```

### 4.2 页面信息架构

- 顶部概览：今日新闻数、热点数、利好/中性/利空计数
- 个股搜索区：个股卡片 → 直接相关新闻 → 关联板块新闻
- 今日重点新闻：跨板块按重要性选取热点
- 板块日报：LLM 归纳当日新闻（可选）
- 板块新闻列表：按已选板块分区展示，相似报道聚合
- 外部事件区：宏观事件及映射板块
- 侧边栏：板块、股票、时间、类型、关键词、来源筛选与配置管理

## 5. 功能需求

优先级定义：**P0 = 缺失则产品不可用；P1 = 显著提升核心体验；P2 = 增值能力。**

### 5.1 新闻采集与去重（P0）

- 按板块关键词定时抓取；交易时段每 30 分钟、夜间每小时一次。
- 增量抓取，仅写入缓存中不存在的新链接。
- URL 归一化 + 标题相似度双重去重，跨来源聚合同一事件。
- 请求超时与连续失败熔断，单一关键词失败不影响其他关键词。

### 5.2 板块分类与外部事件识别（P0）

- 预置 **38 个行业板块**及关键词，覆盖科技、新能源、医药、消费、金融、周期等类别。
- 使用结构化规则识别宏观事件并映射到受影响板块。
- **LLM 只复核规则低置信度样本**，结果按「内容 + Prompt 版本 + 规则版本」缓存。

### 5.3 利好 / 利空与影响力分析（P0）

- 输出情绪（利好 / 中性 / 利空）、影响等级（高 / 中 / 低）、置信度与判断理由。
- 支持同一事件对不同板块产生不同方向的「板块分化」判断。
- 分析结果作为派生数据即时计算，规则升级后历史新闻无需迁移即可重判。

### 5.4 新闻面板与筛选（P0）

- 板块、时间、新闻类型、关键词、来源多维筛选。
- 今日热点：每日 3–5 条高重要性新闻。
- 顶部统计与列表明细口径可对账。
- LLM 板块日报只根据给定新闻归纳，禁止编造；未配置 LLM 时优雅隐藏。

### 5.5 个股搜索（P1）

- 股票代码前缀或名称模糊搜索，精确命中优先。
- 展示行业、市值、上市时间、最新价与涨跌幅。
- 股票 → 板块关联采用「直接映射 → 行业名桥接 → 关键词匹配」三层回退。
- 聚合直接提及该股的新闻与关联板块新闻。

### 5.6 消息推送（P1）

- 支持 Server酱 / PushPlus（微信）与 Telegram。
- 只推政策类或高影响新闻，单次不超过 8 条，按历史指纹去重。
- 每日 7:30 自动生成并推送早报。

### 5.7 配置管理（P1）

- 页面内增删板块、关键词，编辑外部事件规则与板块映射，即时生效。
- 支持增量 / 全量手动刷新，并反馈新增条数与失败警告。

### 5.8 数据持久化与运行基础（P0）

- Supabase Postgres 持久化；未配置时自动回退本地 CSV。
- 缓存保留天数可配置。
- CI 在每次提交后自动运行测试，不通过则不应合入主干。

## 6. 非功能需求

| 维度 | 要求 |
|---|---|
| 性能 | 普通筛选/搜索不触发重新抓取或重算；数据与展示管道采用分层缓存 |
| 可靠性 | 外部请求必须有超时；单点失败降级展示而非崩溃 |
| 成本 | Streamlit Community Cloud + Supabase 免费层 + GitHub Actions；LLM 仅按需调用并缓存 |
| 安全 | 密钥通过环境变量 / CI Secrets 注入，不进入仓库 |
| 合规 | 页面常驻免责声明；自动生成的利好/利空仅供信息参考，不构成投资建议；保留新闻来源与原文链接 |

## 7. 数据指标与验收

| 指标 | 定义 | 目标 |
|---|---|---:|
| 抓取任务成功率 | 成功完成次数 / 总触发次数 | ≥ 95% |
| 数据新鲜度 | 交易时段新闻发布到入库延迟 | ≤ 30 分钟 |
| 去重有效率 | 展示列表中重复事件占比 | ≤ 5% |
| 分类准确率 | 抽样人工评估归入板块的正确比例 | ≥ 90% |
| 推送精准度 | 推送中用户认可「值得推」的比例 | ≥ 80%，单次 ≤ 8 条 |
| LLM 成本 | 需要 LLM 复核的新闻占比 | ≤ 20% |

> 当前为个人项目，指标主要通过自评与抽样核对。若进一步产品化，需要建立正式标注集与线上反馈闭环。

## 9. 风险与依赖

| 风险 | 影响 | 应对 |
|---|---|---|
| AKShare / 东方财富接口变动 | 抓取中断或字段缺失 | 多候选列解析、失败熔断、数据源抽象层 |
| LLM 输出不稳定 / 幻觉 | 误分类、摘要编造 | LLM 仅做复核；摘要禁止编造；所有结论可回溯原文 |
| Streamlit Cloud 休眠 | 页面首次访问慢 | 抓取与推送由 GitHub Actions 独立驱动，与页面解耦 |
| 规则维护成本增长 | 分类准确率漂移 | 规则配置化 + 回归测试 |
| 免费额度限制 | 服务降级 | 缓存保留可配置、抓取频率分时段降频 |

---

## 一句话总结

这个项目不是让 LLM 替用户「判断市场」，而是把重复、分散、难以按板块组织的新闻信息先做结构化预处理：**规则处理确定性问题，LLM 只处理规则拿不准的模糊部分，并保留可解释证据与原文回溯。**
